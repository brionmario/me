Everything changed

From machine code to plain English. Each step changed how we write code.

Act 01 of 5: Everything changed. Pause briefly so the room resets before the new section.

1940s · The language the CPU understands

Machine code

B8 02 00 00 00   ; put 2 in register A
BB 03 00 00 00   ; put 3 in register B
01 D8            ; add B to A

How it worked

Programs written directly in the numbers the CPU understands, with no translation step. They were entered using switches, punched cards or paper tape.

What got easier

Total control. Nothing sat between you and the machine.

What was still hard

One wrong digit broke everything, and the code only worked on that one machine.

Machine code is what the CPU actually runs. Every other language on the next slides gets turned into this before it runs.

The bytes are real x86 machine code (a modern processor, used here for illustration). The comments are only there to explain. The machine sees just the numbers.

Imagine writing a whole program like this, and debugging it by reading numbers. Programmers had to know the number for every instruction.

Early programming was often done by women such as the ENIAC programmers, who worked out programs on paper before setting them up on the machine.

1950s · Names instead of numbers

Assembly

mov eax, 2       ; put 2 in register eax
mov ebx, 3       ; put 3 in register ebx
add eax, ebx     ; eax = eax + ebx

How it worked

Short names like mov and add replaced the numbers. A program called an assembler translated them into machine code.

What got easier

Code became readable. Labels replaced memory addresses, and typos were easier to spot.

What was still hard

Still one line per machine step, and still tied to one type of processor.

Same three instructions as the machine code slide, line for line. Only the way we write them changed.

Assembly is still used today in places like operating systems, embedded devices and performance-critical code.

1970s · Example: C

Compiled languages

#include <stdio.h>

int main(void) {
    int sum = 2 + 3;
    printf("%d\n", sum);
    return 0;
}

How it worked

You write something close to maths and English, and a compiler turns it into machine code. FORTRAN (1957) came first. C (1972) was used to build Unix.

What got easier

The same code runs on different machines. One line does the work of many instructions.

What was still hard

You still manage memory yourself, so crashes and memory leaks are common.

High-level languages actually started in the 1950s with FORTRAN (1957) and COBOL (1959). C, from Bell Labs in 1972, became the language of operating systems and is still everywhere today.

Compilers were a big leap of trust: people worried the generated code would be slower than hand-written assembly. Sound familiar?

C and C++ are still the most common languages in competitive programming because they're fast.

1990s · Example: Python

High-level languages

print(2 + 3)

How it worked

Languages like Python (1991) and JavaScript (1995) manage memory for you and come with huge libraries. The internet made code and answers easy to share.

What got easier

Short, readable code. You rarely start from scratch.

What was still hard

Slower than C, and it became easy to use code you didn't fully understand.

One line. No memory management, no compiling step, no boilerplate.

This era also brought open source and, later, sites like Stack Overflow. Copying code you didn't understand isn't a new problem that AI created.

Python is allowed in most contests, but it can be too slow for tight time limits.

2020s · Describe it, and AI writes it

Natural language

You: Write a program that adds two numbers.

AI:  Here's a Python program:
     a = int(input())
     b = int(input())
     print(a + b)

How it worked

You describe what you want and an AI writes the code. GitHub Copilot (2021) and ChatGPT (2022) made this mainstream, with Claude and Gemini soon after.

What got easier

Anyone can get working code in seconds, for almost any task.

What was still hard

English is ambiguous. We wanted 2 + 3, and it wrote a program that reads input. You still have to check the result.

Point out the mismatch: our prompt was vague, so the AI solved a slightly different problem. It's not wrong, just not what we meant.

That's the theme for the rest of the talk: the tools keep getting better, but understanding the problem and checking the answer are still your job.

Each step hides more of the machine and lets you think about the problem instead.

Walk down the rows. The machine code row is real x86: load 2, load 3, add.

  • Machine code: raw numbers, entered by hand (switches, punch cards).
  • Assembly: human-readable names for instructions. Still one line per machine step.
  • High-level languages (FORTRAN in 1957, then C in 1972): compilers translate for you, and code runs on different machines.
  • Python, Java and friends: memory managed for you, huge libraries.
  • Natural language: describe what you want and an LLM writes the code.

Years are approximate eras, not exact dates.

"The hottest new programming language is English." Andrej Karpathy, 2023

The catch

English is ambiguous. A vague prompt gets you code for a slightly different problem, and it will look convincing.

The skill

Stating a problem precisely: inputs, outputs, constraints, edge cases. Exactly what every contest problem statement does.

If English is the new programming language, then writing a precise specification is the new coding skill.

Point at a contest problem statement: it is a very precise piece of English. Reading and writing those is excellent training for working with AI.

Where AI gets it wrong

AI is impressive. It also gets some very simple things wrong.

Act 02 of 5: Where AI gets it wrong. Pause briefly so the room resets before the new section.

06
Strengths and blind spots

What AI does well, and where it slips

Great at

  • Problems that look like ones it has seen
  • Boilerplate, syntax and standard algorithms
  • Explaining a concept quickly
  • Generating lots of attempts fast

Still slips on

  • Misreading a constraint or a hidden edge case
  • Code that passes samples but fails at scale
  • Being confidently wrong, with a clean explanation
  • Knowing what your real problem is

Keep this balanced, not anti-AI. The left column is real and useful.

Right column: if you can't tell when the answer is wrong, you can't use the tool safely. That's the skill competitive programming trains.

If you have a personal example of AI giving you confidently wrong code at work, tell it here.

Simple questions, confident answers

Things AI models have famously got wrong

How many times does the letter r appear in "strawberry"?

AI 2    Correct 3

Which is bigger: 9.11 or 9.9?

AI 9.11    Correct 9.9

Alice has 3 brothers and 2 sisters. How many sisters does her brother have?

AI 2    Correct 3 (Alice too)

"Which function should I use?"

AI A function that doesn't exist, explained with confidence

Newer models get many of these right, but small changes to the question can still trip them up.

Read each question and let the audience answer in their heads before revealing the AI answer. These are well-known examples that popular models have got wrong.

  • Strawberry: many models confidently said 2.
  • 9.11 vs 9.9: models said 9.11 is bigger, maybe because 11 is bigger than 9, or from version numbers like 9.11 coming after 9.9.
  • Alice's sisters: her brother has Alice plus her 2 sisters, so 3. Models often said 2.
  • Made-up functions: AI sometimes invents library functions or settings that don't exist, and explains them well.

Be fair: newer models handle many of these now. The point isn't that AI is bad. It's that it can be wrong and sound exactly as confident as when it's right.

Point out that both answers sound equally confident. If you didn't already know the answer, you couldn't tell which one to trust.

Results can vary between runs, so if you try it live, have this screenshot as a backup.

Why does this happen?

Generative AI generates. It doesn't count.

ChatGPT, Claude and Gemini are Generative AI. They write an answer one small piece at a time, each time picking what is most likely to come next.

It sees chunks, not letters

Text is split into pieces called tokens. "strawberry" might become str aw berry, so counting letters is surprisingly hard.

It predicts, it doesn't check

"two" sounded like a likely answer, so that's what it wrote. It didn't count the letters unless given a tool to do so.

It sounds sure either way

A wrong answer comes out just as fluent and confident as a right one.

For code The same thing happens with code: it can look clean, sound right, and still be wrong. Someone has to check. That someone is you.

Explain Generative AI in one line: it generates text by predicting the next piece, again and again. It's brilliant at producing likely, fluent answers, but likely isn't the same as correct.

Keep the token explanation simple. The exact split depends on the model, so say "might become".

Calculators didn't make maths useless.
They made understanding maths the part that matters.

AI doesn't remove the need to think. It raises the bar on what you need to think about.

Opens act 3. Bridge from act 2: "If AI can be confidently wrong, someone has to know better. That's the part that hasn't changed."

The core argument of the talk. Nobody hires a human calculator, but engineers who understand maths are paid well, because they know which calculation to do and when the answer is wrong.

Same with code: typing it is cheap now. Knowing what to build, and whether it's correct, is not.

Every step, people said programmers were finished

What changed, and what didn't

What changed each time

  • Less typing, more done per line
  • The machine handled more of the details
  • More people could start programming
  • Software got bigger and more ambitious

What never changed

  • Understanding the problem precisely
  • Choosing an approach that is fast enough
  • Knowing whether the result is correct
  • Debugging when it isn't

The right column is exactly what competitive programming trains.

Key message: each new abstraction was greeted with "now anyone can program". And it was partly true: more people did. But demand for people who could think clearly about problems went up, not down.

Abstractions also leak: when the high-level thing breaks, the people who understand what's underneath are the ones who fix it.

A typical contest problem

Same skills, in a contest

Best Day to Trade

You know a stock's price for the next n days. Buy on one day and sell on a later day. What's the biggest profit you can make? If no trade makes money, print 0.

1 ≤ n ≤ 2·105  ·  1 ≤ price ≤ 109  ·  1 second

InputOutputWhy
7 1 5 3 6 45Buy at 1, sell at 6
7 6 4 3 10Price only falls
50Only one day
3 3 30No change

Looks easy. Let's see which skills it actually needs.

Read the problem and walk through the first test case: the lowest price is 1 (day 2), and the best later price is 6, so the answer is 5.

Point out the last three test cases: they're the edge cases that catch people out. A careless solution might print a negative number for the falling prices, or crash with only one day.

Solution idea (for your reference): go through the days once, remember the lowest price so far, and at each day check "price today minus lowest so far". That's O(n).

Where you build those skills · what competitive programming trains

Six skills in one small problem

01

Breaking problems down

"Best sale on each day = today's price minus the lowest price before it."

02

Complexity intuition

n can be 200,000. Trying every buy/sell pair is too slow. One pass is fast enough.

03

Edge-case paranoia

Prices only falling, only one day, all the same. Each one has a test case.

04

Correctness

Passing the first example isn't enough. You need to know why it always works.

05

Calm under pressure

In a contest, a wrong submission costs penalty time. Check before you submit.

06

Teamwork

One person reads, one codes, one writes test cases. Then swap.

How to train now

Practical habits to stay sharp and learn with AI, not instead of thinking.

13
Using AI to solve your practice problems is like taking a forklift to the gym. The weights go up. You don't get stronger.

Let it land. The struggle is the workout. Being stuck for 30 minutes is when you actually learn.

Keep your mind sharp

Habits that keep you thinking, not just prompting

01

Solve first, ask later

Give yourself 20–30 minutes of real struggle before opening any AI tool.

02

A little, every day

One problem a day beats a weekend binge. Consistency builds intuition.

03

Explain it back

If you can't explain a solution to a friend, you don't understand it yet.

04

Read others' code

After you solve it, read the fastest or shortest solutions. Steal the ideas.

05

Learn one layer down

Know what your tools do underneath: memory, data types, complexity.

06

Compete regularly

Timed contests train focus and calm under pressure, which practice alone doesn't.

14
AI as a training partner

Use it to learn, not to skip

Do

  • Ask it to explain a concept after you've tried
  • Get a hint, not the solution, when you're stuck
  • Have it review your accepted code for a cleaner approach
  • Generate extra test cases and edge cases

Don't

  • Paste the problem in before thinking
  • Copy a solution you can't explain
  • Practise only with AI open beside you
  • Assume its explanation is correct

A simple rule for students: "Struggle for at least 20–30 minutes before asking anything, and then ask for a hint, not code."
